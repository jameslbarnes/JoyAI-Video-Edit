# GPU video jitter follow-up

September 16 overnight regression: a live profile identified work proportional to session age in streaming window selection, called twice per chunk. At approximately 50,000 chunks, it dominated GIL-held samples and sender throughput fell to about 16.4 fps. The streaming paths now calculate only the current window. See [SESSION_AGING_FIX_20260916.md](SESSION_AGING_FIX_20260916.md) for the cause, bounded-work tests, deployment, and long-run monitoring. The priority changes described below did not eliminate this separate aging defect.

September 16 follow-up: the user confirmed playback felt great after the changes, then authorized a 20 Mbps retry. That guarded retry and its 15 Mbps rollback check both detected a roughly 0.3-second intermittent delivery pause with a nonempty queue. The rollback event spent 268.88 ms in GPU preparation. The four-minute success below remains accurate but did not establish long-term absence of pauses. See GPU_VIDEO_QUALITY_20260915.md for the newer evidence. Both priority changes remain enabled; bitrate is restored to 15 Mbps.

User reported jitter after the 20 Mbps quality trial. Restored 15 Mbps first, preserving 2592 x 1440, RIFE 2x/32 fps and SR denoise 0.5. The phone reconnected to the restored stream. A 90-second sender sample was 32.000 fps with zero dropped frames, but a two-minute WebRTC probe subsequently recorded one 297 ms freeze with no packet loss or decoder drops. Average fps and drop counters alone did not detect the reported problem; bitrate alone is not established as the cause.

The output GPU also hosts the fully resident text encoder. Initial GPU transport used ordinary CUDA stream priority for both SR and NVENC preparation. Tested high priority (-1) for the GPU publisher and added bounded delivery-gap diagnostics: timestamps, queue occupancy, transition state, and separate prepare/NVENC/post-sync/pipe durations. These are observational timings and do not change pixels. Priority is a scheduling preference, not guaranteed preemption of running GPU kernels.

First four-minute audit (publisher priority only), SDK `logs/restart-20260915-233536/priority-summary.json` and `receiver.jsonl`: 31.987 sender fps, zero sender drops, 7673 receiver frames decoded, zero receiver freezes/drops/loss. Controlled scene resets and prompt updates ran alongside live Cue. Three sender gaps above 62.5 ms were still observed: 66.7 and 100.9 ms with an empty queue and only a few milliseconds of encoder work, plus 65.6 ms with a queued frame and 34.9 ms prepare wait. Thus absence of receiver freeze counts is not sufficient evidence of smooth pacing. The empty-queue events identify an upstream supply gap; text/SR GPU contention is a hypothesis consistent with shared GPU placement, not fully isolated causal proof.

Extended high priority to PixelUpscaler's CUDA stream so frame production can compete ahead of background prompt work too. Deployment uses the SDK runtime-only restart, preserving prompt, strength, shader routing, resident text and masked prompt graph. No renderer/app build changed. Runtime restart itself is a confound when judging scheduling improvements, because the user previously reported restarts temporarily help. Long-term and actual-device validation remain important.

Focused direct-output/progressive/shader/GPU contract suite: 16 tests passed. After the SR priority edit, five focused progressive/GPU tests passed with PYTHONPATH set to deploy; the first subset invocation lacked that path and failed import, then was rerun correctly. Compile checks passed.

Backups: rollback `logs/restart-20260915-232612/`; publisher-priority deployment `logs/restart-20260915-233141/`; SR-priority deployment `logs/restart-20260915-234007/`. First two diagnostic delivery gaps immediately after encoder startup (536 ms empty-queue warmup and 95 ms mux startup) preceded the steady audit and are retained in health history rather than hidden.

Final validation with SR and publisher priority both -1: SDK `logs/restart-20260915-234629/priority-summary.json`, `audit.jsonl`, `receiver.jsonl`, and `final-state.json`. Four-minute source audit (first five seconds excluded) delivered 31.99994 fps with zero sender drops and no delivery gaps above 62.5 ms. Independent NDI remained 31.940 fps. Median GPU send work was 2.27 ms. The overlapping four-minute local receiver decoded 7672 frames with zero freezes, decoder drops or packet loss. The receiver started later than the source audit and continued beyond it; these are overlapping rather than identical intervals. Controlled scene resets at 45 and 165 seconds, a reversible prompt change at 90 seconds, and live Cue updates were included. Prompt revision numbers reset across scene epochs and must not be subtracted as a global count. Temporary desktop audit hooks were removed and the probe browser exited normally.

During the second deployment the client's first-frame timeout closed the session after cold graph setup. The deployment script failed its initialization check and resumed the operation hold in its finally block. Recovered through SDK multistream remove/add with the current prompt, without another model restart (`logs/reconnect-warm-joyai-20260915.py`). Then restored the saved strength (0.0011044653649249546) and verified fresh configured shader input, resident text and masked graph (`logs/restart-20260915-234605/verified.json`). The same mobile peer was reconnected from the 1080p fallback to joyai-gpu after the initial final-audit checks passed. Final server state confirms only that remote viewer on joyai-gpu, 15 Mbps, over 12,000 sender frames with zero drops and no error.

Current state: 1440p/32 fps/15 Mbps GPU mobile output, both CUDA presentation streams prioritized; 1080p NDI fallback and 720p desktop preview retained. The observed short pauses disappeared in this bounded post-change test. Actual phone display timing and long-term uptime stability have not been measured, so do not claim all possible jitter or memory-growth issues are eliminated.
