# 1440p output trial — rolled back to 1080p

The user requested testing the upscaler's native 2592×1440 output. Added 1440 to the existing output-size and direct-NDI geometry guards. The SR model already computes 4× native input; generation remains 648×360, RIFE remains 2×/32 fps, desktop JPEG preview remains 1296×720, and the mobile publisher remains NVENC at 15 Mbps. Denoise stays 0.5 and neural rendering stays disabled.

Deployed with the established SDK runtime-only restart, preserving current prompt, strength and fresh Easel shader input. Verified fully resident GPU text encoding and the masked prompt graph. The publisher automatically reopened at 2592×1440 and the local WebRTC receiver decoded that resolution.

The trial failed the performance criterion. After an initial five-second exclusion, 60 source samples over 61.46 seconds showed:

| Metric | 1440p trial | Restored 1080p |
|---|---:|---:|
| Fresh NDI frames/sec | 22.62 | 32.00 |
| Desktop presentations/sec | 26.60 | 32.01 |
| Direct sender dropped frames | 341 | 0 |
| Median direct send duration | 46.24 ms | 19.70 ms |
| Median capture-to-desktop latency | 1554 ms | 1438 ms |
| Median generation chunk duration | 472.07 ms | 376.03 ms |

The recovery interval covers 106.45 seconds after excluding its first five seconds. Cue remained active; this is an operational trial rather than a controlled identical-content benchmark. A same-prompt scene reset ran during the 1440p interval and a reversible whitespace prompt update ran after recovery.

At 32 fps each frame has 31.25 ms. The observed 1440p direct-send time exceeded that budget, filling its bounded queue and dropping frames. This establishes a bottleneck in the direct delivery path; it does not isolate the exact cost among RGB-to-RGBA conversion, socket transfer, NDI ingestion and downstream contention. Generation slowed too, so avoiding extra SR neural-network work does not make the whole change free. Desktop presentation had 19 gaps over 100 ms during the failed trial/changeover.

Rolled back atomically to `height:1080` without another model restart. Frame delivery recovered, drops stopped increasing, and a new 65-second WebRTC receiver decoded 2059 frames at 1944×1080 with zero reported freezes, dropped frames or packet loss. The earlier 1440p receiver lost its publisher during intentional rollback and is not evidence of post-rollback playback. Actual phone rendering was not measured.

Current live configuration: `{"height":1080,"direct_ndi":true,"progressive":true}`. The dormant 1440 code support remains available for a later transport-optimization test. Do not re-enable it expecting unchanged smoothness. Higher bitrate cannot fix the measured local frame-delivery bottleneck.

Validation: 14 geometry/direct-output/progressive-delivery/shader-bridge tests passed. Extended the existing preview-separation test to verify both 1080 and 1440 direct output retain a 720p preview; that test passed again after extension. All diagnostic processes completed, browser audit hooks were removed, and SDK operation hold was resumed.
