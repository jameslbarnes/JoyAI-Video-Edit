# Prompt changes and paced playback

Follow-up: the bounded test below missed overlapping scene requests. A later reported reconnect led to additional transition-state and producer-clock fixes; see [WebRTC restart investigation](WEBRTC_RESTART_20260918.md) for the current deployment and validation. The earlier six-minute result is not proof that all scene paths were reliable.

The preceding 23.3–23.7 native-fps result was not sufficient for robust 24-fps presentation. Its limited graph cache still allowed live recapture at prompt-size boundaries, and the fixed output clock eventually drained its reserve when supply ran below 24. Decoder freeze counters alone missed shorter delivery gaps.

## Changes

- Prewarm the complete supported prompt-capacity family (512, 640, 768, 896, 1024) before initializing playback. Live prompt updates only select an already captured graph. Missing warm graphs reject the update while retaining the active prompt; they never drain and capture in the live update path.
- Each graph owns an independent CUDA allocation pool. The family shares only explicit KV buffers and their global publication parity, under the existing model lock. This bounds memory without relying on replay-order-sensitive private pool sharing.
- Native publishers wait for a half-second frame reserve before initial motion and count actual buffer underrun episodes. Existing shader transitions/first-image previews remain separate from fresh generation.
- The input capture clock uses bounded queue feedback (+8% / -4%) to compensate for missed timer slots and refill the native publisher reserve. Capture credit still bounds outstanding work; there are no catch-up bursts.
- GPU encoding is separated from transport pacing. A GPU producer prepares/encodes up to eight frames ahead. `encoded_pacer.py` is a separate standard-library-only process with a 12-frame bounded queue, an eight-frame initial reserve, and its own fractional presentation clock. A feeder thread passes length-framed encoded bytes to it; the pacer writes to the existing parent-owned FFmpeg mux. No inference, tokenizer, or CUDA calls run in the clock process. Queue feedback includes raw, encoded, and pacer queues; the interpolated profile targets 20 queued presentation frames. Shader transitions are sampled in real time rather than rendered in duplicate bursts. Both children and both in-process workers are closed with the publisher.
- The browser retains one bounded interpolation-chunk allowance in its display queue (32 frames for the current 24-fps/2x profile), preventing short JPEG delivery bursts from discarding motion.

## Verification

35 CPU tests passed for graph binding, prompt controls, native publishing, GPU publisher control forwarding, and the isolated pacer. Nine capture-clock/scene-transition tests and 39 client Jest tests passed. The GPU FP8 probe switched arbitrarily among all five captured graphs across 14 short/long/boundary cases; each output matched an independently captured 1024-token reference in the small transformer fixture. It also verified distinct graph pools, shared KV addresses, publication parity preserving the preceding frame's cache, and captured KV stores against eager stores.

Deployment `deployment-230450` prewarmed all five full-model graphs before playback and fit both GPUs. Its initial native-only 840x480/24 trial still depleted the reserve under longer prompts despite no live graph capture. `robust-native24-stress.json` is an interrupted failure diagnostic, not an acceptance pass. The exact owned diagnostic process was stopped; `robust-stress-restored.json` records ownership-checked restoration of the original prompt.

The next trial (`session-231144`) keeps 840x480 and existing SR/output sizes but generates 12 native fps, interpolating 2x on physical GPU0 for 24 output fps. This explicitly trades native temporal sampling for sustained presentation headroom. `robust-rife24-stress.json` measured 249.786 warm seconds, all five graph capacities, 11.990 native / 23.993 GPU output fps, zero output drops/errors/underruns, 1577 ms median capture-to-canvas latency, original prompt restored. It still showed occasional 90–153 ms sender gaps caused by CUDA preparation or NVENC calls occurring at the presentation deadline. This motivated the separate encoded-packet pacing stage; that trial alone is not the final acceptance result.

The encoded-pacer CPU regression injects two 120 ms encoder stalls, checks exact frame order, bounded storage and no underruns, and requires every delivered interval to remain below 75 ms. It passed as part of 34 output/prompt/control tests. Deployment `deployment-232056` contains the encoded-pacer implementation; live results follow after testing.

The in-process threaded version (`deployment-232056`, `robust-final-stress.json`) failed acceptance: prompt changes produced 205–253 ms delivery gaps despite queued encoded frames, with a receiver freeze. This is evidence that moving CUDA work off the sender thread was insufficient while both shared the inference process. It has been replaced by the isolated pacing process in `deployment-233230`. The isolated-process pacing regression also passes with delayed input, exact frame order, zero underruns, and a bounded queue. Latest client tests: 39 Jest plus nine clock/scene tests passed.

## Current live acceptance: deployment-233230

`isolated-pacer-stress.json` completed 248.880 warm seconds across all five prompt capacities: 12.002 native fps, 24.004 canvas fps, and 24.012 paced GPU output fps. Browser output drops, GPU drops, publisher underruns, and errors were all zero. No sender interval exceeded the 62.5-ms delivery-gap threshold. The maximum sampled publisher queue was 22 frames. Median capture-to-canvas latency was 1607 ms. The test was not superseded and restored the original prompt.

Both subsequent scene resets completed without being superseded (`isolated-pacer-scene1.json`, `isolated-pacer-scene2.json`). First-image previews appeared at 1331 / 1349 ms, buffered motion began at 2951 / 2944 ms, and full reveals completed at 3168 / 3194 ms. Maximum measured browser intervals after generated presentation began were 55.4 / 63.0 ms. GPU delivery remained at zero drops, zero underruns, zero recorded gaps, with both transitions completed. These are warm same-content resets; the second changed internal whitespace and restored the original prompt. They exclude speech/Cue latency and do not establish cold-start latency or arbitrary new-scene generation quality.

The current tradeoff is explicit: 840x480 detail is retained, with 12 newly generated frames plus 12 interpolated frames per second. A bounded delivery reserve absorbs production stalls; this does not mean 24 independent model generations per second or zero interaction latency. The compiled VAE remains enabled, and interpolation/upscaling/encoding remain on the second physical GPU. No VSR replacement was introduced.

The concurrent six-minute local WebRTC run (`isolated-pacer-receiver.jsonl`, 360 samples, 2026-09-18 03:39:53–03:45:53 UTC) covered the full prompt stress test and both resets. It decoded 8641 frames at 2592x1440, with zero decoder drops, zero freezes, zero packet loss, and a maximum video-frame callback interval of 54.4 ms. The minimum one-second decoded-frame delta was 24; maximum RTP jitter was 1 ms. This validates the local receiver, not an unobserved remote network. Final readback confirmed the original prompt restored, the tile live, and the 840x480/12-native/2x-RIFE/24-output profile active.
